Dependency Management

When you install several software packages, your package manager warns you about version conflicts before they break your build. Agent Skills have no such safeguard. Load several into one agent session and their instructions can silently contradict each other — one skill telling the agent to send a draft to a second model to sanity-check it, another forbidding any patient data from ever leaving the machine. The Network Analyzer is the missing safeguard: it reads the actual instructions inside a bundle of skills and surfaces how they depend on, overlap with, and conflict with one another before you wire them together.

The four relationships

Every edge in the dependency map is one of four types. Together they answer: is this bundle safe to compose?

Conflict

One instruction permits an action another forbids on the same sensitive object. The hero case — these are the silent contradictions that cause real harm (e.g. a PHI leak). Must be resolved before bundling.

Redundant overlap

Two instructions from different skills do the same job (e.g. two guardrail frameworks both filtering output). Harmless but wasteful — you can usually drop one.

Depends on

One instruction consumes an artifact another produces (a checklist, a redaction map, a structured draft). If you keep the consumer, you need the producer too.

Reinforces

Two instructions push toward the same goal from different skills — mutually supportive. A signal that the bundle is coherent, not a problem to fix.

How the process works

Everything runs offline, against each skill's real repository. No skill text is paraphrased — every node you see in the graph is a verbatim instruction pulled from a live GitHub repo.

  1. Scrape the real repo. For each recommended skill, the pipeline fetches its actual SKILL.md (or README.md) from GitHub via the gh API. Skills with no machine-readable directives — websites, link-lists, plain libraries — are skipped, never invented.
  2. Extract the instructions. It pulls out verbatim directive lines — the modal-verb rules ("never…", "must…", "only…") and imperative steps ("redact…", "quote…", "share the draft…") — while dropping setup and environment noise. Each surviving line becomes one node.
  3. Tag each node with predicates. Every node is annotated with four small properties: its stance / egress (does it open or restrict an action, on what object?), its overlap-class (what job it does), what it produces or consumes, and its goal. This is O(n) work per node, not O(n²) work per pair of instructions.
  4. Derive the edges with a deterministic rule engine. The four relationships fall out of the predicates automatically (see the rules below). No large language model is in the live path — the result is instant, reproducible, and fully explainable: every edge can state exactly why it exists.
  5. Render the dependency map. Nodes are laid out by a force-directed simulation and colored by skill; edges are colored by relationship. Click any node — or any conflict in the side panel — to trace exactly what it collides with.

How a dependency is calculated

The four rules, applied in precedence order conflict > overlap > depends > reinforces (a pair of instructions gets at most one edge, the strongest that applies):

RelationshipFires when…
Conflict One node opens an egress action on an object that another node restricts — on the same object, or on a linked object where one contains the other (a "draft" contains "PHI", an "image" contains "PHI"). That containment bridge is what catches leaks you'd never see reading either skill alone.
Redundant overlap Two nodes share the same overlap-class but come from different skills.
Depends on One node consumes an artifact another node produces. Directed — the arrow points from consumer to producer.
Reinforces Two nodes from different skills share the same goal tag.

Because the rules read explicit predicates rather than guessing from raw text, the engine reproduces every hand-curated edge on our reference bundle with zero false positives, in well under a millisecond — and each edge carries its own "because" explanation.

Worked example — a radiologist drafting reports

The skills our directory recommends for AI-assisted report drafting pull in two different guardrail frameworks doing the same job — a harmless redundant overlap. More importantly, a document co-authoring skill whose "share the draft with a fresh model to sanity-check it" step directly conflicts with a de-identification skill's "no patient data ever leaves the machine" rule. The draft contains patient data, so sending it out is a PHI leak — one you would never catch by reading either skill on its own. It only appears when you examine how the instructions interact. That is exactly what the map makes visible.

What's live vs. draft

Structural relationships (overlap, depends, reinforces) are safe to auto-derive. Conflicts are not — automatically typing a contradiction from keywords alone produces false alarms, so conflicts are shown only on human-verified bundles, each labelled ✓ Human-verified in the analyzer. The remaining pairs are generated as off-server drafts so the work is preserved without shipping unverified conflict claims. Verify a skill's own health separately on the Skill Badges page.

The dependency engine lives in pipeline/rules.py and pipeline/curated.py. Source on GitHub.
